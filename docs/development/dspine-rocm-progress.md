### 64K FlashAttention dispatch inspection (2026-11-15)

- The 64K target attention call has output ne 256,24,7,1 with Q 256 x 7 x 24, K/V 256 x 65536 x 4 and Q4_0 KV cache. Dispatch returns BEST_FATTN_KERNEL_VEC and instantiates `flash_attn_ext_vec<256, 8, 2, Q4_0, Q4_0, false>` (cols_per_block 4 x heads_per_block 2). The RDNA4 WMMA branch needs Q->ne[1]*gqa_ratio_eff > 16, here 7*2 = 14, so the call stays on the vector kernel.
- No FP16 staging is used. `ggml_cuda_flash_attn_ext_get_alloc_size` reports need_f16_K/V false because the Q4_0-Q4_0 instance exists and neither tensor is F32, so `launch_fattn` skips the to_fp16 copies. K is read as block_q4_0, nibbles shifted and dotted against q8_1 Q with dp4a; V is dequantized to half2 inside the KV loop (v_dot2_f32_f16 path).
- Tile: 128 threads (4 warps of 32), 4 columns x 2 heads per block, 2 column tiles x 3 head-pair groups x 4 KV heads = 24 output tiles with KV split over blockIdx.y. LDS is 8,704 B per block (4,096 B KQ half tile, 2,048 B Q q8_1, 512 B Q scales, 2,048 B softmax reduction).
- Compiled resources: 256 VGPRs (the cap), 61 SGPRs, 288 spilled VGPRs, 1,116 B/lane scratch, occupancy 5 waves/SIMD. Neighbouring variants show the 8-row tile is what exhausts registers: `<256,2,2>` spills 11 VGPRs with 40 B/lane, `<256,4,2>` spills 98 with 384 B/lane.
- The other seven-column call, from the draft graph, is `flash_attn_ext_vec<128, 4, 1, Q4_0, Q4_0, false>` with 74 spilled VGPRs, 300 B/lane scratch and 0.174 ms per call.
- Runtime is not limited by KV bytes or math throughput: the 17.25 ms target call moves at most 421 MB of KV (72 MB unique, 6 reads per KV head) = 26 GB/s, and does 11.3 GFLOP = 0.65 TFLOP/s. It is bound by the per-KV-row online-softmax reduction and V accumulation, with spill/reload traffic and 5-wave occupancy on top; dequantization is fused into that loop and is not the limit.
- Evidence: `build-rocm/bench/fattn-vec-res-run.log` (resource-usage compile of `fattn-vec-instance-q4_0-q4_0.cu`) and `build-rocm/bench/gsq-64k-decode-events-20261115-170042.log` for the call shapes.

## Matched 8K GGUF check and prefill architecture options (2026-11-15)

- Ran an order-balanced UD/GSQ diagnostic at 8K with the same 256-token cap, prompt, draft, sampling settings, server executable and HIP DLL; order was UD-GSQ-GSQ-UD. Both GSQ runs used 8192 prompt and 256 output tokens: prefill 255.92 tok/s mean (246.54-265.30), generation 46.47 tok/s mean (46.17-46.77), 208/276 draft acceptance. UD averaged 338.03 / 30.40 tok/s and accepted 183/416. This supports keeping GSQ: its prefill is slower on this prompt, but decode was faster with better draft acceptance. Do not use this one prompt to claim general model quality or decode superiority. Future perf work stays GSQ-only.
- The ISTA prefiller is disaggregated quantization: a separately trained prefill checkpoint paired to a particular frozen decode GGUF, streamed layer-wise from SSD. The published artifacts list UD IQ1/IQ2 variants, not GSQ-RCO, and require NVIDIA Blackwell NVFP4; they cannot be used directly on this gfx1200 GPU. This fork has no ODP implementation. A usable port needs a GSQ-matched, ROCm-supported prefill checkpoint and ODP streaming.
- Causal Encoder-Decoder requires a model trained for that dependency structure; it is not a safe runtime switch for Qwen3.8. SpecPrefill instead drops selected prompt tokens using a lightweight scorer, so it is approximate and changes the context; Qwen3.8's recurrent GDN layers and original-position handling need explicit validation. Do not implement either as a default behavior. Near-term action remains optimizing and measuring the existing GSQ kernels; treat speculative prefill as a separate quality/performance experiment if pursued.
